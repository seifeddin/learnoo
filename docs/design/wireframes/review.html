Flow 3 — Reviewer decision and publication

Wireframe, not production UI. Labels "Teacher", "Teacher + Reviewer" and "Administrator" follow the role model confirmed on 2026-11-24 (DECISIONS.md, Role model). Underneath, the screens depend only on the independent permissions reviewer (per subject), publisher and administrator, which the server checks. Nothing here grants a new permission.

Covers: the decision screen, required comment for "request changes", self-approval denial, approval and publication as separate controls, a stale-publication conflict, the reviewer queue with empty state, and the mobile layout.

3.1 Desktop — assigned reviewer, not the author

Annotations

  1. 1Back to the queue (3.5).
  2. 2Revision context first: author, date, curriculum assignment, published base, link to the previous changes-requested revision and its comment. Advanced diffs are deferred (Phase 2).
  3. 3Decision panel comes after the snapshot in DOM order (read, then decide). A "Aller à la décision" skip link is offered at the top on mobile (3.6).
  4. 4One radio group + one submit button instead of two side-by-side buttons: avoids accidental approval and makes the required-comment rule visible before submitting. Arrow keys move within the group.
  5. 5Comment: required for "request changes" (3.2), optional for approval.
  6. 6Button label states the chosen action ("Envoyer : approuver" / "Envoyer : demander des modifications"). Approval asks for confirmation; the snapshot is never editable here.

The checklist is a reviewer aid. Open whether it is stored with the decision is a schema question for LRN-007; do not treat it as decided.

3.2 Request changes without a comment

  • Whitespace-only comments count as empty.
  • Focus moves to the error summary; the selected decision and the checklist are preserved.
  • On success: banner "Modifications demandées. L’auteur verra votre commentaire." and return to the queue. The author's view is Flow 2.2.

3.3 Self-approval denied — reviewer opens their own revision

  • Explanation instead of disabled buttons: disabled controls are skipped by Tab and screen-reader users may never learn why.
  • The same rule applies to administrators who authored the revision.
  • If a decision request is forged, the server returns 403 and records nothing; the UI shows "Action refusée : vous ne pouvez pas approuver votre propre révision."
  • In the queue, own submissions show "Votre leçon" and open this read-only view.

3.4 After approval — publication is a separate control

  • Approve and publish are never one button. Approval is a review decision; publication is a separate permission and a separate audited action.
  • There is no "override" button in C: reconciliation goes through a new reviewed revision.
  • Open Whether an author holding publisher may publish their own lesson after someone else approved it is not explicitly ruled on; this wireframe neither shows nor forbids it. Needs a recorded decision.

3.5 Reviewer queue (mobile) and empty state

3.6 Mobile decision screen

  • RTL interface: the split view (3.1) swaps sides via logical grid order; snapshot content keeps its own lang/dir.
  • Reviewers can read on a phone, but long math review is expected on desktop unverified.
